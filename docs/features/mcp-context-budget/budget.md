# Бюджет контексту `plune mcp serve`: скільки коштує наш список інструментів

- Дата виміру 2026-11-10; тест `src/mcp-testing/__tests__/plune-tools-budget.test.ts` (`CLI · mcp budget · Plune tools list`), межі в `src/mcp-testing/lint/thresholds.ts` (`PLUNE_BUDGET`).
- Список береться зі справжньої відповіді сервера на `tools/list` (той самий in-memory клієнт, що й знімок контракту), включно з `outputSchema` і `annotations`, а не з визначень контракту.

## Як рахуємо

- `toolListSize` (`src/mcp-testing/lint/size.ts`): для кожного інструмента `ceil(JSON.stringify(tool).length / 4)`, сума за інструментами; найбільший інструмент за назвою.
- Це оцінка без токенізатора: без залежностей і мережі, у CI щоразу те саме число. Тому тест тримає межу з запасом, а не «точну кількість токенів».
- **Оцінка занижена в 1,6–1,9 раза** проти справжнього лічильника токенів (калібрування нижче). Межі лишаються в оцінених токенах: тест стежить за зміною розміру, а не за точною ціною.
- Межа = виміряне × 1,1 з округленням угору (запас 10 %). Межа тримається і знизу: якщо виміряне менше за 0,8 межі, тест теж червоний, тож запас не розповзається непомітно (за запасу 10 % список може зменшитися приблизно на 12 %, далі межу треба опустити).

## Калібрування оцінки (2026-11-10)

Справжню кількість токенів дав безплатний ендпоінт підрахунку токенів одного постачальника моделей (`POST /v1/messages/count_tokens`). Тіло — як у запиті повідомлення: модель, одне коротке повідомлення і `tools`.

- Інструмент для API — лише `name`, `description`, `input_schema` (з `inputSchema` нашого `tools/list`). `outputSchema` і `annotations` API не приймає: запит з ними отримав 400 `tools.0.custom.outputSchema: Extra inputs are not permitted`. Тому модель через цей API бачить список без `outputSchema`.
- Міра: `input_tokens` з інструментами мінус `input_tokens` без них, те саме коротке повідомлення. До цієї різниці входить сталий службовий текст про інструменти: список з одного крихітного інструмента дав +320. «Чисті» токени — різниця мінус ці 320.
- Дві поточні моделі цього постачальника, найбільша й найменша: усі числа збіглися до токена, тож у таблиці один стовпець.
- Оцінка в таблиці — `estimateTokens` на тому самому JSON, що пішов в API, і, для порівняння, на повному записі `tools/list` (з `outputSchema` і `annotations`), який міряє тест.

| Що | Оцінка, JSON для API | Оцінка, повний запис | Реальні, різниця | Реальні, чисті | Чисті / оцінка |
|---|---|---|---|---|---|
| Скоуп `read`, 8 інструментів | 1187 | 2380 | 2184 | 1864 | 1,57 |
| Скоуп `write`, перший список, 17 | 5424 | 8327 | 9242 | 8922 | 1,64 |
| Скоуп `write`, після discover, 22 | 6546 | 10739 | 11167 | 10847 | 1,66 |
| `plune_strategy_propose` окремо | 2005 | 2177 | 3767 | 3447 | 1,72 |
| Відповідь `plune_cases_search` (48 кейсів, українською) як текст повідомлення | 10529 | — | 19376 | — | 1,84 |

Висновки калібрування:

- На англійському JSON одна оцінена одиниця — це 1,6–1,7 справжнього токена, на JSON з українським текстом — 1,84. Гіпотеза «кирилиця дорожча» підтвердилася, але й англійський JSON схем дорожчий за 4 символи на токен.
- Випадковий збіг: оцінка повного запису `tools/list` (з `outputSchema`) близька до справжньої ціни списку без неї (10739 проти 11167). Покладатися на це не варто: для `read` оцінка вища (2380 проти 2184), для найбільшого інструмента нижча в 1,7 раза.
- Правило меж не змінено: межі в оцінених токенах, щоб тест працював без мережі й однаково в CI. Справжню ціну дає множник ~1,7 (англійський JSON) або ~1,85 (кирилиця).

Скрипти калібрування не в репо: вони потребують ключа постачальника. Повторити — тим самим запитом на `count_tokens` для кожного рядка таблиці.

## Відповіді інструментів (живі відповіді демо-проєкту)

Фікстури — **живі відповіді** HTTP API бети для демо-акаунта, проєкт `u-demo-shop::default`, зняті 2026-11-10 лише читанням: зібраний `plune mcp serve` через stdio викликав `plune_project_context`, `plune_cases_search` (`limit` 100) і `plune_review_list`, а відповіді платформи записано в `src/mcp-testing/__tests__/fixtures/plune-budget-live.json` (60 КБ, без обрізання). `plune-budget.fixtures.ts` віддає їх за шляхом і запитом.

- Очищення перед записом: id автора кейсів замінено на `u-john-doe`; два інші проєкти акаунта отримали вигадані id і назви, їхня компанія — `Example Corp`. Адрес пошти, імен людей і токенів у відповідях не було; тест `the recorded answers hold no address, token or user id but the sample ones` стежить, щоб так і лишалося. Назви кейсів, наборів і черги демо-магазину лишено як є (українською).
- Місій у демо-акаунті немає, тож `plune_mission_get` міряється на синтетичній місії з 5 джерелами (John Doe).
- Живий вимір через stdio і вимір на фікстурі трохи різняться: живий сервер запущено з `--project`, тому `projectId` у відповіді `plune_project_context` заповнено (548 проти 543), а заміна id автора скоротила сторінку кейсів на 8 (10529 проти 10521). Межі взято з виміру на фікстурі, бо саме його рахує тест.

Рахується текстовий вміст відповіді (`content[0].text`, JSON з відступом 2), бо його читає модель; `structuredContent` несе ті самі дані.

## Висновки

- Постійна ціна кожного запиту — 8327 токенів для `write` і 2380 для `read`. Чверть списку `write` (2177) — один `plune_strategy_propose` через вкладену схему стратегії; це перший кандидат на скорочення.
- `outputSchema` — близько 28 % списку `write` (8327 → 6029). Клієнт, який не передає її в модель, платить менше; які клієнти це роблять, тут не перевірялося.
- Приховування п'яти інструментів заощаджує 2412 токенів на запит (29 %), тож воно себе виправдовує.
- Найдорожча відповідь — сторінка кейсів: 48 живих кейсів коштують ~10,5 тис. оцінених токенів (~219 на кейс), тобто ~19,4 тис. справжніх. Повна сторінка зі 100 таких кейсів — орієнтовно ~22 тис. оцінених і ~40 тис. справжніх токенів (екстраполяція, не вимір). Відступи у тексті відповіді додають близько 37 % (10521 проти 7690).
- Що можна скоротити (окремими задачами, у цьому PR інструменти не змінюються): схему `plune_strategy_propose`; відступи в тексті відповіді; меншу верхню межу `limit` у `plune_cases_search` (зараз до 100) або підказку в описі брати менші сторінки.
- Межу на кількість видимих інструментів (`MAX_VISIBLE_TOOLS` = 20) і її тест не змінено.
