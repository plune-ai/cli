# Spec — C4-reporter-env

> **Епік:** `plune-ai/plune#486` (B-2) · **Сусід:** [`C1-reporter-core`](../C1-reporter-core/spec.md)

## 1. Context

Конфіг Playwright лежить у git. Ключ прогону, токен і розмір батча — ні: вони різні для ноутбука,
на якому конфіг писали, і для раннера, який його виконує. C1 приймає їх як опції; CI-джобу треба
дати їх, не редагуючи закомічений файл.

**Що знайшлося при реалізації:** з десяти змінних, які епік перелічує, **чотири не мають куди
приїхати**. `runs` несе `kind`, `externalKey`, `configuration`, `meta{sha,branch,ciUrl,runner}` і
`statusEvent` — ані назви, ані середовища, ані міток, ані групи. Це заведено як **D13** у
`02-features.md`.

## 2. Goals

1. CI-джоба задає налаштування репортера через оточення, не чіпаючи конфіг.
2. Явно передане в конфізі виграє в оточення.
3. Змінна, якої платформа не вміє зберегти, **називається вголос**, а не мовчки зникає.

## 3. Non-goals

- Автовизначення CI (`GITHUB_SHA`, `branch`, `ciUrl`) — епік цього не просить, а вгадувати, який
  саме CI, — це окрема розвилка.
- `PLUNE_CREATE` — сходинка драбини C2, реалізується там.
- Поля прогону з D13 — це зміна платформи, не CLI.

## 4. User stories

- **US-01:** Як інженер CI, я задаю токен через `PLUNE_TOKEN`, бо `plune login` на раннері нема кому запустити.
- **US-02:** Як інженер CI, я даю всім шардам один `PLUNE_RUN` і отримую один прогін.
- **US-03:** Як інженер CI, я кажу `PLUNE_PROCEED=1`, бо закриваю прогін окремим кроком.
- **US-04:** Як інженер, я хочу дізнатися, що `PLUNE_ENV` не працює, — від репортера, а не з різниці між тим, що я налаштував, і тим, що бачу.

## 5. Acceptance criteria

| # | (US) | Критерій |
|---|---|---|
| AC-01 | US-01 | `PLUNE_TOKEN` стає токеном; без нього лишається сховище `plune login` |
| AC-02 | US-02 | `PLUNE_RUN` стає `externalKey`; процеси з однаковим значенням дають один прогін |
| AC-03 | US-03 | `PLUNE_SHARED_RUN` або `PLUNE_PROCEED` лишають прогін відкритим — так само, як шард |
| AC-04 | — | `PLUNE_API_URL`, `PLUNE_BATCH_SIZE`, `PLUNE_FALLBACK` заповнюють свої поля |
| AC-05 | — | Явно передане в конфізі виграє; явний `undefined` — **не** «скинути», бо це розкриття необовʼязкового поля, а не рішення |
| AC-06 | — | Порожня або пробільна змінна — це «не задано». CI-шаблон лишає саме таку, а порожній `externalKey` платформа відхиляє: усі безключові прогони зіткнулись би на одному записі унікального індексу |
| AC-07 | — | Прапорець читається **за значенням**: `PLUNE_PROCEED=0` у комірці матриці — це вимкнено |
| AC-08 | — | `PLUNE_BATCH_SIZE`, що не є додатним цілим, ігнорується, а не перетворюється на `NaN` |
| AC-09 | US-04 | `PLUNE_RUN_TITLE / ENV / LABELS / GROUP` називаються в одному рядку як проігноровані |

## 6. Non-functional requirements

Жодної нової залежності: читання оточення — це `process.env` і три функції розбору.

## 6.1 Security / privacy

`PLUNE_TOKEN` проходить тим самим шляхом, що й збережений токен: у клієнт і нікуди більше.
У лог не потрапляє (C1 AC-12), у fallback-файл теж.

## 7. Test plan

Юніти на `readEnv` — по одному на критерій, плюс тест адаптера, що `PLUNE_PROCEED=1` дає
`leaveOpen` там, де без нього був би `finish`. Той самий шов, що й у C1: чиста функція над
переданою мапою оточення, тож жодних `vi.stubEnv`.
