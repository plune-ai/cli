# 0001 — Один CLI і стандартні формати

- **Status:** Accepted
- **Date:** 2026-10-10
- **Deciders:** Leonid (AZANIR)

## Context

Клієнт підключає Plune до свого CI і не хоче ставити окремий пакет під кожен фреймворк. Сьогодні є
один CLI (`@plune-ai/cli`) і один тонкий репортер, `@plune-ai/playwright`; обидва користуються
спільним ядром `reporter-core` (ADR 0001 у `C1-reporter-core`). Файли (скріншоти, трейси,
логи) кладуться в бакет клієнта за тимчасовими посиланнями на запис (cli#82):
ключів бакета в CI немає.

Питання: як звітують pytest, Maven, Jest, Vitest, PHPUnit, Cypress, .NET — репортер на кожну мову
чи звіт, який фреймворк уже вміє писати сам.

## Decision

1. **Один CLI і стандартні формати.** Живий репортер лише для Playwright. Інші фреймворки — тільки
   на явний запит клієнтів. Фреймворк пише стандартний звіт своїм вбудованим репортером, а
   `npx -y @plune-ai/cli run import <звіт>` читає його без встановлення.
2. **Вкладення беруться зі стандартних форматів**, а не з «репортерів для Python, Java, C#»:
   - JUnit XML: явна позначка `[[ATTACHMENT|path]]` на окремому рядку в `system-out` або
     `system-err` тесту — її розуміють Jenkins і GitLab;
   - Allure: каталог `allure-results` — результати, кроки, вкладення тесту, кроків і фікстур.
     Каталог читається без прапора; `source` вкладення проходить ту саму
     перевірку шляху, що й позначка JUnit. Через Allure вкладення дає й Jest (`allure-jest`), якому
     JUnit цього не дає.
3. **GitHub Action** `plune-ai/report-action` — зараз, за зразком `eval-action`.
   Docker-образ CLI для GitLab, Jenkins і Azure — коли попросить перший
   клієнт не з GitHub.
4. **Цей ADR** — у першому PR епіку.

Файли з імпорту йдуть тим самим шляхом, що й з репортера: `reporter-core` (бакет за посиланням,
`direct` для картинок і тексту, назва, якщо бакета немає), з тими самими лімітами й попередженнями.
Нового шляху завантаження імпорт не має.

**Доповнення (03.11.2026): `run import` читає й теку JUnit-файлів.** Maven Surefire
(`target/surefire-reports`) і Gradle (`build/test-results/test`) пишуть по `TEST-<клас>.xml` на клас, і вся тека
стає одним прогоном. Для Java тоді не потрібна залежність `allure-jupiter`. Рішення оператора: «А (рекомендую):
навчити run import читати теку JUnit-файлів підтримую робим». Правила:

1. Без `--format` тека, у якій є хоч один звичайний файл `*-result.json`, — це Allure, як і раніше. Інакше це
   JUnit: кожен звичайний файл `*.xml` у самій теці, за назвою файла. Підтеки (`binary/` у Gradle) не
   обходяться, посилання не відкриваються.
2. `--format junit` читає теку як JUnit, `--format allure` — як Allure, `--format playwright-json` на теці
   відхиляється.
3. `*.xml`, що не є JUnit, пропускається, і про це є рядок у виводі.
4. Тека без `*-result.json` і без JUnit-файла — помилка, що називає обидва формати (код виходу 2).

Позначка `[[ATTACHMENT|path]]` рахується від теки свого XML-файла, як і для одного файла. Пункти 1, 3 і 4
розділу Decision це доповнення не змінює; у пункті 2 «каталог читається без прапора» тепер стосується теки з
`*-result.json`.

## Consequences

- Для клієнта: один рядок у CI, один секрет `PLUNE_TOKEN`, жодного пакета під фреймворк.
- Відповідальність за вкладення лежить на тесті: він має надрукувати позначку. Це видно з
  прикладів для pytest і Java в README. Звіт, який ніде не пише вміст `system-out` у `testcase`
  (`jest-junit` пише консоль на рівні набору), не дає вкладень, і ми не вгадуємо, якому тесту
  вони належать.
- Файла, на який посилається звіт, може не бути (workspace очищено). Імпорт тоді **не падає**:
  кожен такий файл має окремий рядок у виводі (тест і шлях зі звіту), у кінці є підсумок
  «Imported N results · M files uploaded · K files not found». Прапор
  `--fail-on-missing-attachments` дає код виходу 1 для команд, яким потрібен червоний CI.
  Тихе відкидання, як у Testomat.io, свідомо не береться.
- Шлях позначки перевіряється після `realpath`: відносні шляхи рахуються від теки звіту, а все, що
  веде за її межі (`..`, абсолютний шлях, symlink), відхиляється з тим самим рядком, і файл не
  читається. Звіт з чужого CI не може відправити в бакет `/etc/passwd`.
- Список відсутніх файлів CLI збирає в одному місці (`missingAttachments` результату імпорту).
  Коли сервер Plune матиме стан «файла не було під час імпорту», його відправка буде однією
  правкою там. Сервер цього стану поки не має.
- Окремі пакети під Python, Java чи C# не з'являться, поки цього не попросить клієнт.
